# 判断原則の台帳（v1）

- 状態: **v1、ユーザー承認済み（2026-10-09）。** 以後の判断要求は §3 の手順と書式で出す。原則の変更はユーザーだけが行う（§3.3）。
- 作成: 2026-10-09（ユーザー指示。経緯は `docs/10月９日のメモ.md` の「監査を通していくだけなら律速的に出来るのでは」への返答）
- 目的: これまでのユーザー決定に繰り返し現れる原則を明文化し、判断要求のうち原則で決まるものを減らして、
  監査が判断待ちで止まらないようにする（律速性の確保）。原則は判断を**代行**するためではなく、
  **どの問いが本当にユーザーの判断を要するか**を見分けるために使う。
- 出典の表記: 決定日と、その決定が記録されている場所。

## 1. 原則

### P-01 外から目標を持ち込まない
規範（豊かさや何かへの選好）を、構成的な定義（世界であること、自己維持であることの条件）へ持ち込まない。
目標や選好は、持ち込むならメタ層で、監査できる形で持ち込む。

- 由来: E1（個体内発展公理）不採用、静的豊かさ公理 AX_rich 不導入（2026-07-08、`category/erie_c_axiom_categorical_memo.md` §11-2）。
  κ に選好を入れない（2026-09-08、`specs/drafts/reactivation-substrate-profile-v1-items.md` の前提 (3)、解析計画の forbidden_adjustments）。
- 使う問い: 定義に「望ましさ」「豊かさ」「最大化」が入り込みそうなとき。
- 理論との関係: M4（外部 set point の不注入）と層分離の、判断の場面への適用。

### P-02 産出は行為を介する
構成素の産出・依存を認めるのは、運動ユニット（行為）を経るときに限る。行為を経ない相互依存は
「抽象化された関連性」であって組織ではない。

- 由来: M1 の Φ = π⋆∘ρ⋆（理論の定義）。運動を経ない相互依存は組織でない（2026-10-02、`specs/packets/DC2-HUNIT-N3.md` §6 決定1）。
- 使う問い: 依存や組織の正解・定義に、運動ユニットを経ない経路が入るか。
- 注意: 「行為を経る」を両方の向きに要求するか片方で足りるかは、この原則だけでは決まらなかった（P-06 との衝突、決定7）。

### P-03 部分（ユニット）を単位に読む
担体はユニットであり、冗長性・依存・支えはユニットの水準で読む。経路や辺の水準の区別を単位にしない。

- 由来: 構成素 C = ユニット（2026-09-08、profile 草案の前提 (1)、解析計画の forbidden_adjustments「C = units を変えない」）。
  冗長は部分で読む（2026-10-02、DC2-HUNIT-N3 §6 決定3）。
- 使う問い: 冗長・依存・単位をどの粒度で数えるか。
- 注意: 「部分」のうちどれを見るか（対の両端か閉路の全員か）は、この原則だけでは決まらなかった（決定6、新しい判断）。

### P-04 介入は発信停止だけとし、その帰結は副作用込みで読む
測定の介入は発信停止に限る。停止の副作用（抑制の解除など）を判定から除くための別の介入を足さない。

- 由来: 介入は発信停止のみ（2026-09-28、`specs/packets/RSB-GEN-001.md` §3）。停止の副作用込みで可（2026-10-02、決定4）。
- 使う問い: 測定や正解の定義に、別種の介入（辺の除去、状態の固定など）を持ち込むか。
- 注意: 辺の除去は「正解を独立に作るための検査器」としては使ってよい（判定そのものには使わない）。

### P-05 導出できない数値の閾値を置かない
根拠から導けない数値の閾値で判定しない。閾値が要るように見えたら、論理的な条件（有無、一致・不一致、
正解との照合）に置き換える。

- 由来: 基体を Lenia から離散グラフへ（2026-09-09、DC 判定がしきい値に媒介されるため）。
  N3 の撤回条件の 5% を撤回して正解照合へ（2026-10-02）。冗長性の閾値 X = 0.5 を廃止して dc と dc_T の結論比較へ（2026-10-07、
  `specs/packets/RSB-PLAN-002.md` §14）。
- 使う問い: 判定・撤回・報告の条件に割合や数値の境目が出てくるとき。
- 注意: 測定の窓や horizon のように、基体の定義の一部として事前登録で凍結する数値は対象外（P-08 で縛る）。

### P-06 反証可能性を残す側を選ぶ
二つの案が同程度に正当なら、結果が定義を否定しうる側を選ぶ。照合が自明に一致してしまう正解や定義は採らない。

- 由来: 行為は片方の向きで足りる（2026-10-04、決定7、「反証可能性を残すため」と明言）。
  「有無」ではなく正解照合を選んだ（2026-10-02）。DISCRIMINATION（全件通過・0件通過で基体を棄却）。
- 使う問い: 正解や判定の定義が、検証対象の定義とほぼ同じになりそうなとき。

### P-07 主判定と確定した定義は変えず、新しい読みは記録として並べる
確定した主判定（DC）や登録済みの定義は差し替えない。新しい読みは診断や感度読みとして並べて記録し、
代わりの認証にしない。未批准の実験的な定義（DC2 など）はこの原則の対象外で、改訂してよい。

- 由来: DC を主判定とし DC2 は全 case で記録（2026-09-27、`specs/packets/RSB-001.md` §14）。
  hSelf_T を診断欄として記録（2026-10-07）。design-r2「冗長な系を既存 DC で認証する代替証明としない」。
  運動ユニットの行為の読み方は既定のまま（2026-10-03、決定5）。
- 使う問い: 測定や定義の改良案が出たとき、置き換えるか並べるか。

### P-08 事前登録は強める側を選び、結果を見る前に固定する
登録・束縛・凍結は、結果を見た後で動かせる余地が少ない側を選ぶ。結果を見た後の調整は禁じる。

- 由来: 登録媒体は検証時の live remote 照合（2026-09-17）。追記のみの登録表と取り下げ（2026-09-27）。
  解析計画の改訂と再登録を1回にまとめる（2026-09-28）。既知の差分の登録簿を digest で縛る（2026-10-09）。
  解析計画の forbidden_adjustments（通過率を見た後に閾値・窓・反証行・解釈を変えない）。
- 使う問い: 何をどこまで登録で縛るか、いつ固定するか。

### P-09 証拠がなければ決めずに未決として残し、毎回報告する
判断の材料がそろっていない論点は、決めずに「未決」として記録し、関係する出力のたびに報告する。

- 由来: N3 の損失合成による余分な対と E1 型の合併を未決のまま残す（2026-10-04）。
  運動ユニットの行為の読み方を「未来の自分」に残す（2026-10-03）。
- 使う問い: 推奨案はあるが、ユーザーが決め手を持たないとき。

### P-10 安全装置は構造で作る
守りを「追加の仮定」や「守られた選択肢」で作らず、逃げ道が構造的に存在しない形で作る。逃げ道を作るには
監査可能な外部公理の注入を要するようにする。

- 由来: 機能終了の不可逆性（2026-07-20、反セルフハック）。層分離と Σ-purity。
- 使う問い: 安全装置や禁止事項をどう設計するか。

### P-11 主張は検証できた範囲に限る
検証した範囲を超えて主張しない。現象的な語（意識、死）を形式主張に使わない。有限の不在を一般の不可能性に
昇格させない。

- 由来: `phenomenal_claim = :not_certified` の絶対条項。「死」の語を使わない（2026-07-19 整理）。
  有限モデル監査の4値（`general_impossibility = not_established`）。
- 使う問い: 結果をどう書くか。これは判断の原則というより常設の制約で、判断要求を減らす効果は小さい。

## 3. 判断要求の手順

### 3.1 振り分け

| 種類 | 条件 | 扱い |
|---|---|---|
| A | 一つの原則が一つの案に決める | エージェントが推奨案で進め、§4 の決定ログに「原則 P-xx を適用、確認待ち」と記録する。ユーザーは後でまとめて確認し、異議があれば覆す |
| B | 複数の原則が別の案を指す | ユーザーが判断する。決定ログに、どちらの原則を優先したかを残す |
| C | どの原則も当てはまらない | ユーザーが判断する。決定から一般化できる原則があれば、この台帳に足す（台帳の変更もユーザーの承認を要する） |

**種類によらず、取り消せない操作（登録表への追記、push、本番 run、登録済みファイルの変更）はユーザーの承認を待つ。**
A で進めてよいのは、取り消せる作業（作業ツリーの変更、試験、試算）に限る。git の commit と push は、
リポジトリの作業指針（CLAUDE.md）どおり、ユーザーに依頼されたときだけ行う。

### 3.2 判断要求の書式

```text
問い:
種類: A / B / C（根拠となる原則: P-xx, ...）
候補と推奨:
帰結の試算（証拠のパス）:
反証条件:
取り消し可能性: 可逆 / 不可逆
エージェント側の検証: 別コンテキストの検証、変異試験、独立実装との照合のどれを済ませたか
```

最後の欄は、エージェントの誤りが判断要求として上がるのを防ぐためのもの。済ませていない検証があれば、
判断を求める前に済ませる。

### 3.3 原則台帳を守る規則（グッドハート対策）

1. 原則の追加・変更・削除は種類 C の判断であり、ユーザーだけが行う。版と日付を残す。
2. 結果を見た後で、その結果の解釈を変えるために原則を変えてはならない（解析計画の forbidden_adjustments と同じ扱い）。
3. 原則の適用は、原則を定めた後の問いにだけ行う。過去の決定を原則で上書きしない。
4. 原則を調整に使ったデータとは別のデータで、定義を評価する機会を設ける。8 ユニットの本番 run は、
   N3 や正解の調整に使っていない規模の回路での最初の評価になる。

## 5. 計測と反証条件

週ごとに数える: 判断の件数、そのうち A の割合、問いから決定までの時間、後で覆った決定の割合、
判断要求のうちエージェントの誤りだったものの割合。

**この台帳の反証条件**: 導入後の判断で A の割合が増えず、B と C が大半を占め続けるなら、律速の原因は手続きでは
なく概念の未成熟であり、この台帳では速度は上がらない。また、A として進めた判断がユーザーの確認で頻繁に
