## 1. 確定すること・しないこと

**確定する**: 基体（何を測るか）と解析計画（結果をどう解釈するか）を別々に凍結し、
それぞれの digest を登録記録へ置き、run 開始前に登録を確認する機構を作る。

**確定しない**: 候補の軌道、α/σ/π/ρ の測定、`ERIEState` の構成、`check_DC` の評価。

## 2. 主張できることの限界（契約に明記する）

> 本機構が保証するのは「信頼する管理 runner が、固定 remote 上の登録を確認したうえで
> 当該 profile で run を開始した」ことに限る。リポジトリ外での事前探索の不存在は証明しない。
> 同一主体が作成できるローカルログの真正性も保証しない。
> **任意の Julia コードからのトークン偽造防止も主張しない**（Julia に access control は無い）。
> 信頼対象は管理 runner であって、敵対コードに対する security boundary ではない。

**「事前登録」を「探索不存在の証明」と呼ばない。**

## 3. 二つの digest と、その境界

| digest | 対象ファイル | 覆う内容 |
|---|---|---|
| `profile_blob_sha256` | `reactivation-substrate-v1.toml` | 基体、観測規則、測定プロトコル、列挙方針、**出力 schema・全 case 記録・必須生データ** |
| `analysis_plan_digest` | `reactivation-analysis-plan-v1.toml` | 反証条件、**解釈・撤回/停止判断・禁止する調整**、通過0件時の扱い、欠落重複の扱い |

**改訂1 で両ファイルに「報告規則」があり重複していた。** 境界を上表のとおり定める。
profile 側は**何を出力するか**、analysis 側は**それをどう読むか**。
矛盾時の優先順位は作らず、**重複キーを schema で禁止する**（codex (e)）。

版も2本に分ける。`profile_schema_validation_version` と
`analysis_schema_validation_version` を独立に持つ。

digest は raw bytes の SHA-256（ユーザー決定 2026-09-17）。
正規化を廃した代償として、**exact schema 検証に成功した場合にのみ** `VerifiedRegistration` を
生成し、トークンと run 開始レコードへ両方の validation version を記録する。
**版を記録するだけでは適用の証拠にならない**ため、生成条件に組み込む（codex (e)）。

RSB-003 の反証条件は、ファイルを RSB-003 の packet で作ってよいが、
**最初の候補 run より前に `analysis_plan_digest` へ含まれていなければならない。**

## 4. 未知の節・キーを拒否する

「digest は全 bytes」と「覆うのは指定の節だけ」は、指定外を禁止する schema がなければ矛盾する。
両ファイルとも exact schema とし、未知の節・未知のキーを拒否する。

**両ファイルにまたがる重複キーの全面禁止は改訂3 で撤回する**（codex (e)3）。
`profile_id` や `schema_version` のような join field まで排除してしまうため。代わりに
両 schema の key set を明示的に分離し、**共有してよい identity field だけを allowlist** として
列挙し、その値が一致することを検査する。優先順位を作らない方針は維持する。

## 5. capability トークン（主張の水準を下げる）

```
verify_substrate_registration(registration_commit, ...) -> VerifiedRegistration
start_run(token::VerifiedRegistration, ...) -> ...
```

`start_run` を**サポートされる唯一の公開 run 開始 API** とし、トークンを必須引数にする。

改訂1 の「型の上で経路を存在させない」は**「サポートされる公開 runner API に経路を置かない」へ
弱める**（codex (c)）。Julia では unexported も inner constructor も security boundary ではない。

**本単位で実装するもの**: `verify_substrate_registration`、`VerifiedRegistration` 型、
登録・run 開始レコードの validator、完了 manifest の雛形。

**本単位で実装しないもの**: `start_run` の実体と run の接続。これは RSB-002/003 の義務である。

したがって**本単位のゲートは「未来の API が存在すること」を証明しない**（codex (e)5）。
§9 の完了照合は validator と雛形に対する検査であって、実際の run に対する検査ではない。
報告でこれを混同しない。

## 6. 三つの記録と、何をどこで固定するか

| 項目 | 登録レコード | run 開始レコード | 完了 manifest |
|---|---|---|---|
| `profile_blob_sha256` | **確定** | 実読 bytes から再計算して照合 | 参照 |
| `analysis_plan_digest` | **確定** | 再計算して照合 | 参照 |
| `profile_commit` | **確定** | 参照 | 参照 |
| `registration_commit` | **書かない**（自己参照） | **確定**（run 時 checkout から明示入力） | 参照 |
| 固定 remote URL / 固定 ref | **確定**（定数として登録 schema に置く） | 照合 | 参照 |
| remote 照会結果（observed OID） | — | **確定**（run 開始時に保存） | 参照 |
| `profile_schema_validation_version` | **確定** | 照合 | 参照 |
| `analysis_schema_validation_version` | **確定** | 照合 | 参照 |
| runner commit（完全 SHA） | 未定 | **確定** | 完了時に再検査し exact equality |
| runner HEAD tree OID | 未定 | **確定** | 完了時に再検査し exact equality |
| `dirty=false`（untracked 含む） | 未定 | **確定** | 完了時に再検査 |
| `Manifest.toml` raw SHA-256 | 未定 | **確定** | exact equality |
| `Julia VERSION` | 未定 | **確定** | exact equality |
| `run_id` | — | **確定** | 参照 |
| `run_start_record_digest` | — | **確定** | **開始記録を権威として参照** |
| canonical ordered case IDs + count + `case_digest`（§7b の規則） | 未定 | **確定** | 完全一致したときのみ `status=complete` を原子的に発行 |
| `author_declared_at` | 記録する。**自己申告 metadata であり順序判定に使用しない**と schema と出力に固定 | — | — |

**expected case「集合」では順序違反を落とせない**（codex (a)）。順序付きの case ID 列と件数と
その digest を run 開始前に固定し、完了時に順序まで照合する。
「同値を照合」という曖昧な表記は改訂3 で廃し、各欄を exact equality か参照かに分けた（codex (b)）。
runner の source/tree digest という斜線表記も廃し、commit・tree OID・dirty を独立の欄にした。

## 7. registration_commit の決定方法と固定 remote（改訂3 で profile_commit 束縛を追加）

**(1) `registration_commit` は導出せず明示入力とする。** run 時の checkout が指定した値を
`verify_substrate_registration` の第一引数に取る。current checkout HEAD・registry 最終更新
commit・行の初出 commit はいずれも異なりうるため、暗黙に選ばない。

**(2) 固定 remote URL と完全修飾 ref は validator schema に埋め込んだ literal const とする。**
**登録行の自由入力にしない。** 自由入力にすると、別の自己管理 remote を行に書いて通せる
（codex 改訂2 レビュー (a)）。ref は短縮名ではなく完全修飾名（例 `refs/heads/main`）。

**(3) 取得はローカル object DB を信頼しない。** 一時 bare repo に固定 URL の完全修飾 ref を
**一度だけ** fetch し、その OID を `observed_remote_oid` とする。`ls-remote` と `fetch` を
分けるなら両 OID の一致を確認し、ref 移動の TOCTOU を避ける。

**(4) 権威は registry 行であって呼出側の期待値ではない。**
`registration_commit:specs/substrate-registry.toml` を bytes として読み、exact schema で
一意な `registration_id` の行を選び、その行が指す2つの path を bytes として読んで SHA-256 を
計算する。**呼出側が渡した「期待行」を権威にしない。** tree entry の mode が通常 blob である
ことも検査する（symlink 不可）。

**(5) 検査する条件（改訂2 の4条件に profile_commit 束縛を追加）。**

```
(i)   registration_commit の tree に registry 行と profile / analysis の両 blob が存在する
(ii)  その blob の SHA-256 が登録値と一致する
(iii) **profile_commit の tree にも同じ path・同じ raw bytes が存在する**
(iv)  **profile_commit から registration_commit まで、その2 path の bytes が不変である**
(v)   registration_commit が固定 remote の固定 ref から到達可能である
(vi)  registration_commit が profile_commit の子孫である
```

**(iii)(iv) が改訂2 に欠けていた。** 改訂2 は registration_commit の tree しか見ないため、
**`profile_commit` が任意の古い祖先でも通ってしまい、「profile commit P」の束縛になっていなかった**
（codex 改訂2 レビュー (a) の重大な欠落）。

**(6) `observed_remote_oid` を run 開始レコードへ残す。**

**(7) remote へ到達できない場合は `UNVERIFIED` とし、成功として扱わない。**

## 7b. 順序付き case digest の再現規則

`count` と ID 列だけでは digest の再現規則が未定義になる（codex (e)2）。次を exact に定める。

- ID の文字集合と正規化（許可文字、UTF-8、長さ上限）
- 区切り方式（length-prefix を用い、区切り文字に依存しない）
- 末尾改行の有無
- 並び順の規則（profile の `case_order` から一意に決まること）
- digest algorithm と `case_digest_version`

## 8. DC を持ち込めなくする（隔離の実装）

**改訂1 の想定は誤りだった。** `test/parallel_test_worker.jl` は2行目で `using ERIEC` するため、
`test_substrate_registry.jl` を計画表へ直接載せると**隔離検査にならない**（codex (c)、実機確認済み）。

**(1) root 側のテストは subprocess 起動だけにする。**

```
julia --startup-file=no --project=tools/SubstrateRegistry \
      tools/SubstrateRegistry/test/runtests.jl
JULIA_LOAD_PATH=@:@stdlib
```

subprocess suite なので `ERIEC_EXCLUSIVE_TEST_FILES` へ入れる。

**(2) 最小 Project 自身が依存遮断を検査する。**
`Base.find_package("ERIEC") === nothing`、stdlib 以外の依存が無いこと、
source と include の allowlist を検査する。**これが依存遮断の証拠**であり、
root の全体 `Pkg.test()` は統合確認にとどまる。

**(3) exact schema で表現不能にする。** 登録レコードと run 開始レコードの schema を、
`hSelf`/`hSMC`/`hAct`/`hBound`・関係・軌道の各フィールドが書けない形に定める。

**(4) grep は補助検査。**

**(5) production CLI も隔離する**（codex (e)1）。`bin/eriec-substrate-registry.jl` 自体を、
最小 Project を `--startup-file=no` と `JULIA_LOAD_PATH=@:@stdlib` で起動する launcher にする。
**root project から直接 include / using できる入口を「対応 API」にしない。**

## 9. 反証条件（`analysis_plan_digest` 側に置く）

| ID | 内容 | 期待 |
|---|---|---|
| `FALSIFICATION-RSB-001-BLOB` | profile を 1 byte 変更 | 照合失敗 |
| `FALSIFICATION-RSB-001-COMMENT-ONLY` | コメントのみ変更 | 別 digest で失敗 |
| `FALSIFICATION-RSB-001-UNKNOWN-KEY` | 未知の節・キー・両ファイル重複キー | exact schema が拒否 |
| `FALSIFICATION-RSB-001-UNREGISTERED` | 登録記録に無い digest | 失敗 |
| `FALSIFICATION-RSB-001-BOTH-SWAPPED` | profile と期待 digest を両方差替え | registry 行との突合で失敗 |
| `FALSIFICATION-RSB-001-ANALYSIS-DRIFT` | 解析計画のみ変更 | **旧 registration での verify が失敗**（digest が動くだけでは不足） |
| `FALSIFICATION-RSB-001-ANALYSIS-BOTH-SWAPPED` | 解析計画と呼出側期待 digest を両方差替え | registry 行との突合で失敗 |
| `FALSIFICATION-RSB-001-ORDER` | case ID の順序を入替え | 完了照合が失敗 |
| `FALSIFICATION-RSB-001-RUNNER-DIRTY` | runner が dirty | トークンを生成しない |
| `FALSIFICATION-RSB-001-NO-MEASUREMENT` | RSB-001 の artifact または API に測定値・DC 値が存在 | 単位の失敗 |

**live remote 契約は `REMOTE-UNREACHABLE` 一件では不足**（codex 改訂1 レビュー (d)）。
**ローカルの bare remote fixture** を用意する。まず**同一 fixture の valid baseline が成功する
テストを置き**、そこから1条件だけ変えた6件を個別に落とす。

| ID | valid baseline から変える1条件 |
|---|---|
| `FALSIFICATION-RSB-001-REMOTE-WRONG-REF` | 完全修飾 ref が存在しない |
| `FALSIFICATION-RSB-001-REMOTE-REG-UNREACHABLE` | ref は存在し registration object も fixture 内にあるが ref の祖先でない |
| `FALSIFICATION-RSB-001-REMOTE-NOT-DESCENDANT` | 両者とも ref から到達可能だが registration が profile の子孫でない（merge tip 等） |
| `FALSIFICATION-RSB-001-REMOTE-PROFILE-BLOB-MISMATCH` | ancestry と reachability は正常で **profile tree の blob だけ**不一致 |
| `FALSIFICATION-RSB-001-REMOTE-REG-BLOB-MISMATCH` | ancestry 正常で **registration tree の blob だけ**不一致 |
| `FALSIFICATION-RSB-001-REMOTE-UNREACHABLE` | transport 失敗 → `UNVERIFIED` |

**改訂2 の `REMOTE-PROFILE-UNREACHABLE` は独立でないため削除した**（codex 改訂2 レビュー (c)）。
registration_commit が固定 ref から到達可能かつ profile_commit の子孫なら、
profile_commit も必ず同じ ref から到達可能になる。したがってこの条件だけを壊すことはできず、
壊せば `REG-UNREACHABLE` か `NOT-DESCENDANT` も同時に壊れる。
代わりに `PROFILE-BLOB-MISMATCH` を置き、§7(iii) の profile tree 束縛を検査する。

**実 GitHub への照合は登録実行時のゲートでのみ行い、通常の unit test を
ネットワーク依存にしない**（codex (d)）。

## 10. 禁止変更

`phenomenal_claim` を動かさない。`specs/ledger.toml`・`formal/`・`src/` を変更しない。
候補の数値を通過率を見て調整しない。本単位では通過率を得ない。
κ に選好を入れない。C = ユニットを変えない。
登録レコードに自分自身のコミット SHA を書かない。
`origin` や remote HEAD をローカル設定から暗黙取得しない。

## 11. 探索用 basis

候補の数値を使わず synthetic fixture のみ。`profile_id` に `scratch` を含め登録レコードに載せない。
結果を candidate の設計判断に使わない。用途は配管の検証に限る。

## 13. 本単位の完了条件を二つに分ける

§3 は RSB-003 の反証条件を最初の候補 run より前に `analysis_plan_digest` へ含めることを要求する
一方、本単位は実ファイルを凍結・登録する。両立させるため完了を二段に分ける（codex (e)4）。

**完了A（機構実装完了）**: validator、トークン型、レコード schema、反証16件、隔離構成が揃う。
RSB-003 の条件が未確定でも成立する。

**完了B（最終登録完了）**: `reactivation-substrate-v1.toml` と
`reactivation-analysis-plan-v1.toml` を実際に凍結して登録レコードへ載せ、remote へ push する。
**RSB-003 の反証条件が analysis 側へ凍結された後でなければ成立しない。**

**登録前の候補 run は完了A の後でも禁止する。** 走らせてよいのは完了B より後に限る。
