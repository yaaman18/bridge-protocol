## 1. 目的・解く問題

測定エンジン（`tools/ReactivationMeasurement`）は ERIEC に依存しない（RSB-GEN-001）。DC と DC2 を case 記録に
当てるには、ERIEC とエンジンの両方に依存するプラグインが要る。RSB-PLAN-002 §3 の束縛はそのパッケージの
ディレクトリ単位なので、DC・DC2 の判定コードはすべてそのディレクトリの中に置く。

## 2. 確認済みの証拠

- case 記録 `rsb-case-record-v1` は全ユニットについて π, ρ, α, σ をビットマスクで持つ（`formats.jl`）。
  ρ はすでに出力ユニットに制限済み。α, σ は全ユニットの最終状態の変化で、入力・出力への制限は読み手が行う。
- 判定基準は case 記録と宣言した構造（n, inputs, outputs, out_adjacency）だけを受け取り、系を見ない（`criteria.jl`）。
- out_adjacency は重みと環境写像の両方の辺を含む（`substrate.jl`）。profile の `boundary_edge_sources` と一致する。
- DC2 の Julia 実装（`tools/model_audit/DC2.jl` の `check_dc2`）は、直接の量化式との全符号化照合、Lean 参照模型、
  変異試験、正解照合を通っている（`logs/gates/DC2-AUDIT-20260930/` 以降）。

## 3. 設計

### 3.1 パッケージ

`tools/ReactivationERIEC`（RSB-PLAN-002 の仮称どおり）。依存は ERIEC（リポジトリ直下）、ReactivationMeasurement、TOML。
判定基準は2つ。

| criterion_id | criterion_version | 型 |
|---|---|---|
| `dc` | `dc-rsb003-v1` | `DCCriterion` |
| `dc2` | `dc2-m1r-n3-rsb003-v1` | `DC2Criterion` |

### 3.2 case 記録から ERIE の対象への読み替え（両判定基準で共通）

ユニット i（0 始まり、記録のビット i）を記号 `:u<i>` とする（profile の命名と同じ）。

- C = 全ユニット、M = 出力ユニット（outputs）、E = 入力ユニット（inputs）
- α(m) = alpha[m] ∩ E（m ∈ M）、σ(e) = sigma[e] ∩ M（e ∈ E）、π(m) = pi[m]（m ∈ M）、ρ(c) = rho[c]（記録で M に制限済み）
- κ = kappa、ε = epsilon

### 3.3 DC

`ERIEC.check_DC(ERIEState)` をそのまま使う。境界は profile の `boundary_rule = "outgoing_nonzero_edges"`：
κ のユニットのうち、out_adjacency に κ の外のユニットを持つもの。

- values = `dc, hSelf, hSMC, hAct, hBound`（RSB-PLAN-002 §4.3）
- diagnostics = `act, boundary, kappa_nonempty, epsilon_nonempty, mask_self, mask_smc, mask_act`（§5.2 の定義どおり。
  `collective_only_change` は `future_final` から、どの単独停止でも最終状態が変わらず、ある複数停止でのみ変わるユニット）

### 3.4 DC2

DC2 の判定コード（`check_dc2` とその補助関数）を `tools/ReactivationERIEC/src/dc2_core.jl` に移し、
`tools/model_audit/DC2.jl` はそのファイルを `include` する。これで監査が検証したコードと本番で束縛されるコードが
同じファイルになる。

- values = `dc2, hSelf2, hSMC, hHingeNeeded, hUnit, beta_nonempty`
- diagnostics = `act, beta, sigma_cover, mutual_pairs, hUnit_v1, irreducible_units`
  （`hUnit_v1` と `irreducible_units` は旧 hUnit の記録で、DC2 批准の資料。判定には使わない）

## 4. 仮説・未検証部分

- 記録から ERIE の対象への読み替え（§3.2）が `tools/model_audit` の回路測定と同じ意味であること。
  検証: 同じ回路を両方の経路で測り、DC・DC2 の値が一致するかを照合する（§6）。

## 5. 推奨案と棄却した代案

- DC2 のコードを複製せず移す（推奨）。複製すると監査済みのコードと束縛されるコードが別物になり、ずれても気づけない。
- DC の境界を `beta` にする案は棄却。解析計画 v2 は DC の境界をグラフ境界、DC2 の境界概念を beta として並べて記録する
  （LEAN-AUDIT 誤り1の訂正）。

## 6. ゲート

1. プラグインの試験（`tools/ReactivationERIEC/test/runtests.jl`）:
   - 判定基準の適合性（`check_criterion_conformance`）。値・診断のキー集合が §3.3・§3.4 と完全一致。
   - DC: 直接の量化式（ERIEC を使わない）による参照実装と、ランダムな記録で一致。
   - 解析計画 v2 草案の反証行のうち `PENDING-RSB-003` だった欄を、プラグインで照合する。
   - 回路監査との一致: `tools/model_audit` の探索領域の回路を、エンジンの Substrate として測り直し、プラグインの DC・DC2 と
     ModelAudit の DC（`check_dc_pattern`）・DC2（`check_dc2`）が一致する。
   - scratch 登録で `start_run` を通し、2つの判定基準が全 case を判定する。
2. 既存の DC2 監査の試験（`test/test_dc2_*.jl`）が、コードの移動後も通る。
