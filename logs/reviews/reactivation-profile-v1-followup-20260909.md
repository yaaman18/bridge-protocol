# 再活性化基体 v1 追加レビュー

結論: git を登録媒体に使う案は可能だが、**祖先関係＋過去blobのdigest一致だけで事前登録を保証する案は challenge**。
2026-09-09、claude `[AUTO 2/10]` の4点への回答。ユーザー未決の提案を読取監査した。
実装、草案・台帳・formal・srcの編集、ゲート実行、commit/pushは行っていない。

## 1. 推奨3 — challenge（git方式自体は排除しない）

`git merge-base --is-ancestor P HEAD` が確認するのはDAG上の到達可能性であり、
測定・評価の実行時刻やpushの先後ではない。P=HEADでも成功する。
例えば、ローカル測定→profile commit P→結果commit R→両方push、という順序でも
PはRの祖先であり、Pのblobのdigestも一致する。履歴書換え・force-pushは不要。
これはリポジトリ外の探索だけの問題ではなく、管理対象のrunnerが登録確認を実行前にしない場合の穴。

証拠の読み分け:

- `specs/ledger.toml:168` の evidence_commit は既存証拠のコミット束縛の先例。
  実験前の登録を検証する契約の先例ではない。
- `git show 34be987` は「過去履歴を今回書き換えていない（force-pushなし）」という作業記録。
  変更対象もcommit-msgフックとCHANGELOG。将来のforce-pushを防ぐリモート制約や、
  測定開始前の登録を証明する仕組みはこのコミットからは確認できない。
- 前回案の「信頼する記録先」は別製品・外部DBを必須としていない。信頼境界を定めたgitリモートも候補。

最小修正候補:

1. 登録先リモート/refと登録済みPの完全なcommit IDを固定し、**各run開始前**に登録を確認する。
   Pは結果から後付けで選ばせず、記録するrun IDをPに結び付ける。
2. 測定・評価runnerが読んだprofileの正規化digestをPの対象blobと照合する。
   過去blobだけが一致しても、実行時に別ファイルを使う穴が残る。
   schema/正規化版・プロトコル版・実行コードrevisionも記録する。
3. 登録確認→run開始→完了manifestの順序を、信頼するrunner/CIの記録として保存する。
   run終了後だけの祖先検査に置き換えない。成果物を収めるcommitはPの厳密な子孫とできるが、
   それだけでは実行順序の証拠にはならない。
4. 全case manifestの欠落・重複・途中停止とprofile差替えを検査する。これは祖先検査とは別の責務。

この前提を信頼するとき「管理されたrunは登録済みprofileを使って開始した」と主張できる。
記録外の探索や、同じ主体が自由に捏造できるローカルログの真正性まで保証しない。
新規サービスは必須でないが、「追加は検査1つ」では不足。git方式の採否はユーザーへ返す。

## 2. C/D — 実装コストのみ比較（採否の推奨なし）

N=全ユニット数、I=入力集合、L=k+1、Ew=Wの非零有向辺数とする。
同じ窓・同じκ・同じ測定済み関係を用いる比較であり、wall-clock計測は行っていない。

| 選択 | 計算と追加作業 |
|---|---|
| C: 最終ステップε | 最終配置の入力だけを抽出。O(\|I\|)。時刻とwarm-up規則の固定が必要。 |
| C: 窓全体ε | 単独なら入力ごとのL点ANDでO(L\|I\|)。現κが同じ窓のpersistent unitsなので、κを既に計算する場合は **ε=κ∩I** としてO(\|I\|)で抽出できる。既存のκ用窓以外の履歴は不要。窓の一致と途中offのケースの検証が増える。 |
| D: 無向in∪out | Wを一度走査し両向き隣接を保存、O(N+Ew)。重複処理を含め隣接エントリは高々2Ew。各supportの境界走査もO(N+Ew)。 |
| D: outのみ | 同じWを走査し出方向だけ保存、O(N+Ew)、エントリ高々Ew。漸近計算量は同じで、主な差は定数と入辺しかない頂点の期待値。 |

N≤16ではいずれも小さな集合・配列処理。実装量の主な差は抽出規則・fixtureの期待値であり、
凍結・provenance・全件manifestの整備が両案に共通して必要。
W_envを除外するコストも両境界案で同程度。ただしこれは境界が表す接続の意味の選択なので、
「環境経路を含む全グラフの境界」とは書かない。

比較ラベルの修正: 「緩い/厳しいDC」という全順序は未成立。
窓ε⊆最終εならσ⋆が集合の合併であるためActは縮小し、hActだけは厳しくなる。
しかしhSMCは **X⊆T′(X)** でXが両辺にある（`formal/ERIEC/Hinge.lean:8`, `DC.lean:16`）。
T′が単調でもpost-fixed条件の真偽はXの包含に関して単調でない。
型に適合する有限関係の反例は次のとおり（基体上の測定可能性までは主張しない）:

- σ(a)={m}, σ(b)=∅, α(m)={a} ならX={a}でhSMC=true、X={a,b}でfalse。
- σ(a)={m1}, σ(b)={m2}, α(m1)={b}, α(m2)={a}ならX={a,b}でtrue、X={a}でfalse。

したがってC変更のDC通過率の方向を型から断定できない。
Dは同じsupport・同じWに限りboundary_out⊆boundary_undirectedなのでhBoundについて順序がある。
この修正は選択の推奨ではなく、ユーザーへ提示する比較の正確性のため。

## 3. 非空性の記録 — accept（新規RSB出力に置く候補）

推奨は **RSB checkerの診断出力として計算し、その出力を結果certificate/manifestへ保存**。
既存 `DCResult` の5フィールド（`src/dc.jl:110-116`）やcheck_DCの返却契約は変更しない。
新規RSB wrapperが対象caseのκ/εを決定的に算出し、4述語と同じ状態・窓・関係から
`kappa_nonempty`, `epsilon_nonempty` を導出する。
certificateに保存されたBooleanを入力の自己申告として信頼せず、再検証時に再計算・照合する。
台外データなど不正入力は、診断対象の正当なDC=falseケースと区別する。

非空フラグは説明用で、DCへの第五・第六の条件ではない。
Act≠∅は既存定義上κ≠∅かつε≠∅を含意するため、DC=trueのケースで空性を別途排除する必要はない
（`formal/ERIEC/DC.lean:31-49` の空伝播）。falseの原因と部分述語の自明な成立を見せるために有用。

RSB guarantee文の候補:
「同一caseのκ・ε・4関係・境界に対するhSelf/hSMC/hAct/hBoundと非空性を記録する。
κ=∅ならhSelf、ε=∅ならhSMCは空集合の包含により真となる。
いずれかが空ならhActは偽でDCは不成立。非空性フラグは診断情報である。」
「含意の成立と区別しない」という文面は避ける。空集合の包含も元の述語の正しい成立であり、
診断情報が区別するのは空の場合と非空の場合。
既存dc.system全体をlesion固有の説明に変更せず、新規RSB契約の範囲に記載する。

## 4. 推奨1のassumptions — clarify（独立性の免責だけでは未完）

π/ρの方向は引き続きaccept。共通baseline、同一case/介入期間/読取窓/優先順位を指定した上で
`D_s(x)=Persist(base_s)\Persist(lesion_s(x))`,
`π_s(m)=D_s(m)`, `ρ_s(c)=D_s(c)∩O` とする候補に、最低限次を加える。

- 状態/窓/horizonに依存する単一off介入の喪失関係。別状態への一般化、on介入の十分性、
  産出との同値、冗長原因の完全検出は保証しない。抑制解除による増加は喪失差分に含めない。
- M⊆Cで同じ物理ユニットに同一protocolを適用する場合、**ρ_s(m)=π_s(m)∩O**。
  単に「独立ではない」だけでなく、この整合条件を確認する。
  traceの共有を明示し、role別hashを独立実験の証拠にしない。
  同一hash禁止の既存草案§6とは両立方針が未決なので、黙って採用しない。
- baselineでpersistentな出力m自身をoff固定するなら、対象自身を除外しない定義では
  m∈π_s(m)かつm∈ρ_s(m)。直接強制された自己喪失を含めるかを凍結する。
  含めるなら、その自己ループによるhSelfの部分的成立を独立した自己産出の証拠と解釈しない。
- baseline/lesionの初期状態、開始・終了時刻、warm-up、窓、介入優先順位、集約の有無、
  全C/Oを覆う試行の対応をprofileとtraceに結び付ける。

hSelfの説明も **κ⊆π⋆(ρ⋆(κ))という二段の関係像のpost-fixed条件** と記載する。
「依存の閉包」は直観として使えても、Φの冪等性・拡大性や因果依存の推移閉包まで意味しない。
`formal/ERIEC/Closure.lean:7-15` は合成を定義しており、このlesion解釈を定理として証明していない。

## 関連する事実誤認の短い補正

- 有限台check_DCがfalseを返すのは台の不正または4述語不成立であり、hGC=falseの検出ではない
  （`src/dc.jl:133-150`）。hGCを要求するコンストラクタとの二経路の意味を混ぜない。
- 閉世界だけでは全offへの到達・吸収は従わない。θ≤0なら自発onが可能で、θ>0でも
  自己維持するon軌道からoffへ到達するとは限らない。非空性診断は有用だがこの到達性を根拠にしない。
- 上界方式Fは候補として可能。ただしΣabsの計算そのものを機械Intでoverflowさせないよう、
  検証段階は任意精度またはchecked算術とし、typeminのabs、閾値の表現可能範囲、
  実行Int幅/固定幅の選択も検証対象にする。実行更新をBigInt必須とする意図ではない。
